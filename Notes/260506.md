虚拟内存
- 父子进程的相同变量，看似位于内存中的相同地址
- 原因：每个进程都使用一个虚拟地址空间
  - 好处：在编写程序时不需要考虑是否与其它进程产生冲突
  - 操作系统需要实现从逻辑地址（虚拟地址）到物理地址的**地址转换**
  - 跨进程的共享可能较为困难，但对于多任务系统是必要的
- 不使用虚拟内存？
  - 物理内存的使用率可能较低；内核给每个进程分配一个不冲突的内存物理起始地址/终止地址，但进程通常不会完全占用这些空间
  - 某些进程（如数据库）在运行过程中可能会请求大规模的内存

虚拟地址的映射方式
- 查找表：地址数量*地址位数
  - 简单的查找表开销过大
- 解决方案：部分查找表，只对高位逻辑地址映射到高位物理地址，而保持低位逻辑地址与物理地址相同
  - 分页思想：高位的部分查找表称为**页表** Page Table，低位的不变部分称为 Page Offset
  - 每个 Page 中的逻辑地址要求映射到连续的物理地址，但 Page 之间不要求映射到连续的物理地址
  - 物理内存的分配**以 Page 为粒度**（最小单位），相比直接以字节为粒度更加高效
  - 问题：每个 Page 内部可能存在内存浪费
    - 解决思路：让多个进程共享 Page 内的未使用部分？
    - 需要监测每个 Page 内空间的空闲情况，**带来额外开销**
    - 在*浪费比例不高*的情况下，通常忽略 Page 内部的空间浪费

页表设计
- 内容：映射、权限信息、valid bit
  - 权限信息：读写权限、共享权限
  - valid bit：当前页是否活跃（被使用）
- 性能权衡：页表过大时，查找性能下降
  - 改进方案：多级页表，细化粒度
  - 映射到单一页表改为进一步拆分高低位，分别映射到不同级的页表（附图）
  - 对于 32 位系统，通常拆分出 **2 级页表**即可
  - 最外层页表的基地址存储在一个寄存器中，**在进程运行时加载**；内层页表的基地址由上一层页表指出
  - 大页表
  - 缓存：使用 TLB(Translation Lookaside Buffer)

其它类型页表
- 哈希页表：需要关注碰撞处理
- 倒置页表：物理地址中的条目更稀疏，反过来将物理地址映射到逻辑地址
