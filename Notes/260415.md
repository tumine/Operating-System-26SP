三个问题
- [**哲学家用餐问题**](https://gemini.google.com/share/54d2333ad2dc)
  - **互斥要求**：不允许两人同时使用一只筷子
  - 最基本的解决方案：检查两只筷子是否同时可用，只有同时可用时才进行饮食
    - 筷子是共享对象
    - 如果每个哲学家都拿起右手边的筷子、等待左手边的筷子，就会产生死锁
  - **同步要求**：避免死锁
  - 改进方案：先拿一只筷子，看另一只筷子是否可用；*如果不可用，则放下已经拿到的筷子*
    - 破坏了“占有并等待”的要求
    - 存在问题：可能出现一种特殊序列，每个哲学家都在不停地“拿一只筷子-释放”，但**没有任何进展**
  - 上述解决方案的共同点：筷子是共享对象
    - 一个哲学家用餐时，左右的哲学家不能用餐；本质上**与筷子无关**
  - 新的方案：把**哲学家的状态**作为共享对象
    - 需要引入 `EATING`、`THINKING`、`HUNGRY` 状态
      - `THINKING` ：刚吃完，正在执行 `think()` 操作
      - `HUNGRY`：执行完 `think()` 操作，需要用餐
      - `HUNGRY` 状态类似 Peterson 的解决方案，有资源需求但暂未占用资源
    - 利用互斥锁保证只有一个哲学家可以进入 `take()/put()` 函数
    - 一个哲学家从 `EATING` 切换为 `THINKING` 时，**唤醒其左右的哲学家**
- **生产者-消费者问题**
  - 考虑有限 buffer 的情形
  - 管道的适用范围有限：不能解决多生产者-多消费者的情形
  - 信号量的解决思路
    - 互斥要求：二进制信号量 `mutex`
      - 在修改 buffer 共享对象时上锁
    - 同步要求：两个计数型信号量 `empty/full`
      - buffer 满时生产者需要挂起，buffer 空时消费者需要挂起
      - 生产者在插入 buffer 前执行 `down(&empty)`，在插入后执行 `up(&full)`
      - 消费者在从 buffer 读数据前执行 `down(&full)`，在读数据后执行 `up(&empty)`
      - `empty` 统计空 slot 的数量，`full` 统计已占用 slot 的数量；因此会出现生产者和消费者分别**只对两个信号量进行单边操作**
      - 在操作前执行的 `down()` 操作兼做为可行性检查；如果 buffer 空/满，对应的 `down()` 操作会被阻塞
    - 需要注意 `mutex` 和 `empty/full` 的修改顺序：必须先修改 `empty/full`，再修改 `mutex`，否则会导致死锁
- **读者-写者问题**：并发数据库问题
  - 多个读者希望同时对一个数据库进行访问，同时有一个写者希望写入数据库；不允许同时执行读写操作
  - 使用两个信号量 `mutex` 和 `db`（数据库访问权）
    - 第一个读者开始读取时执行 `down(&db)`，最后一个读者读取完后执行 `up(&db)`
  - 读并发性：如果已经有读者在读取，就允许新读者直接进来一起读取
    - 可能把写者长时间阻塞
    - [如何给予写者更高的优先级？](https://gemini.google.com/share/248ce960146f)
