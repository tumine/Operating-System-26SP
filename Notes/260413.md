信号量：一种数据类型
- 在抽象层次上可以定义为一个整数，但在具体实现中一般比整数类型复杂
- 用于多个进程对一个共享对象的访问，表示有几份资源可以同时被访问
  - 二进制信号量：可用于实现互斥锁
  - 计数信号量：控制有限数量资源
- 原子操作：`P/V`，减少/增加信号量
  - 为直观起见，也可记作 `down()/up()` 或 `wait()/signal()`
  - 在进入/退出临界区时调用

如何利用信号量控制共享资源的访问？
- 信号量非零时，允许进程访问，并减少一个信号量单元
- 信号量为零时，阻塞进程访问

如何实现信号量？
- 简单实现：类似于此前互斥锁的实现；**忙等**
- 改进：没有可用资源时挂起 `special_sleep()`
  - 引入等待队列：在信号量数据结构中增加一个链表存储等待资源的进程
  - 保证原子性：信号量（共享对象）的修改过程应禁用中断
  - 两个进程可能**同时被唤醒并尝试进入临界区**（执行 `down()` 操作），此时通过禁用中断可以强制只有一个进程可以进入临界区
- 多核环境下如何保证进程同步？自旋锁+中断管理
  - 用自旋锁控制多核并发
  - 在单核环境下利用中断进行管理

Memory Fence：作为内存屏障，起到同步作用
- 确保在*编译器打乱指令执行顺序*的情况下，仍然能够执行完 Memory Fence 之前的所有代码

信号量的三大用途
- 实现访问互斥（二进制信号量）
- 计数：例如数据库中统计并行读/写操作进程数
- 进程同步：可能会用到多个计数型信号量

如何执行进程同步？
- 管程：封装对信号量的原子操作，确保外界对信号量的修改必须按照指定的方式进行修改
  - 定义了对共享对象的访问调用
  - 避免对 `P/V` 操作的调用不正确或不完全引发的问题
- 活性：希望进程有执行进展
  - 活性失败的例子：无限等待、死锁
    - **无限等待**：进程在请求资源，但永远无法请求到
    - **死锁**
- 性能上的要求：希望控制进程进入临界区的解决方案对性能的影响尽可能小
  - [无锁算法](https://gemini.google.com/share/5c726d4b4c4e)：通过 CAS(Compare And Swap) 实现对共享资源的并发访问
    - 每个对共享资源的修改请求都包含共享资源地址（V）、**预期原值（A）**和新值（B）；只有 V 上的值确实等于 A 的情况下才将其修改为 B
    - 锁：在每次尝试访问共享资源前都假定有另外的进程正在访问；是一种**悲观假设**
    - 在竞争冲突特别严重的情况下，互斥锁的解决方案仍然更适合

死锁
- 背景：同一个临界区可能同时希望访问多个共享对象；不同进程对于多个共享对象执行 `down()` 操作的顺序可能不同
- 可能出现的问题：两个进程各自拥有部分进入临界区所需的资源，同时**等待对方释放剩下的一部分资源**
- （**重要**）发生条件
  - **互斥**：共享对象的访问是互斥的
  - **占有并等待**：占有部分资源，并等待取得剩余的资源
  - **不允许抢占**：进程不允许从其它进程抢占后者占有的资源
  - **循环等待**：多个进程形成一个等待关系上的循环
- 如何处理？
  - 检测与恢复：利用额外的方式检测系统中的死锁并进行处理
    - 死锁处理的难点主要在于检测
    - 资源分配图：刻画资源分配的基本情况
      - 节点：进程（圆圈）、资源（方框，包括对其类型和数量的描述）
      - （有向）边：请求边（进程请求资源，但**未获得**）、分配情况（资源按进程的请求提供给进程）
      - （**重要**）检测死锁：看图中是否出现圈
        - 在单实例条件下，有圈即代表出现死锁
        - 在**多实例**条件下，如果其中一个实例被分配给一个圈外的进程，就可能不构成死锁
        - 在判断死锁时**默认互斥、不允许抢占这两个条件成立**
        - 如何判断多实例条件下的死锁？**矩阵描述**
          - 总资源：$\vec{E}=(E_1, E_2, \cdots, E_m)$
          - 可用资源：$\vec{A}=(A_1, A_2, \cdots, A_m)$
          - 资源分配矩阵：$\left[C_{ij}\right]$，$C_{ij}$ 表示第 $i$ 个进程**实际持有**第 $j$ 种资源的数量
          - 资源请求矩阵：$\left[R_{ij}\right]$，$R_{ij}$ 表示第 $i$ 个进程**希望持有**第 $j$ 种资源的数量
          - 不断判断是否有进程的资源需求已经被满足（$\vec{R_i} \leq \vec{A}$），运行这些进程并执行 $\vec{A}=\vec{A}+\vec{C_i}$
  - 预防：如果当前资源的分配可能导致死锁，就拒绝按当前方案分配资源
    - 根据死锁发生的四个条件进行判断，**不让四个条件同时满足**
  - 避免：在资源分配时执行前置判断，避免出现死锁
    - 仍然使用 $(E, A, C, R)$ 的矩阵描述
    - 定义**安全状态**：存在一个执行顺序保证所有进程的需求都能被满足
    - 定义非安全状态：不管让什么进程先运行都无法满足所有进程的需求
      - **非安全状态 $\neq$ 死锁**：进程手上持有的资源可能仍能支撑进程运行一段时间
    - 在分配资源之前**先判断分配之后的状态是否安全**；如果分配之后的状态不安全，就拒绝此次分配请求
  - 忽略：“鸵鸟算法”，什么都不干
    - 假定死锁没有发生
    - 不花费大开销执行死锁的处理，而是直接杀死其中的部分进程
    - 场景预设：死锁发生不是很频繁，简单处理的后果对于用户来说可接受
      - 不适用于安全性要求较高的情形
